根据用户需求生成或优化 Claude Code 技能（Skill）。产出的技能必须做到：**功能目标单一明确、逻辑清晰简要、轻重分明**——AI 读后能无歧义地理解"何时触发、做什么、怎么做、什么不能做"。

## 核心原则

1. **理解优先**：动手前必须充分理解用户意图。优化已有技能先通读并按【质量红线】诊断不足；关键信息缺失时用 `AskUserQuestion` 提供选项澄清，绝不靠猜。
2. **单一职责**：一个技能只解决一类明确问题，核心目标能用一句话说清。若需求混杂多个目标，建议拆分为多个技能，或引导用户聚焦核心目标。
3. **为 AI 而写**：技能的读者是 AI 而非人。每条指令必须具体、可执行、无歧义；删除一切不影响执行的背景性解释，保持高信息密度。
4. **轻重分明**：主文件 SKILL.md 只放高频必需信息（建议 ≤200 行）；大段示例、模板、参考资料分离到 `examples/` 等子文件按需引用。硬性约束与柔性建议用词区分（"必须/绝不" vs "优先/尽量"）。
5. **自由度匹配**：根据任务性质决定指令约束程度——结果开放、依赖判断的任务给原则性指导（高自由度）；容易出错、格式敏感的任务给精确步骤甚至固定模板（低自由度）。
6. **保留与增强**：优化已有技能时，必须保留原有核心功能与业务逻辑，只做结构重构、去冗、补齐与规范化，严禁擅自删功能。
7. **引用机制**：文档内用【xx】标记内部引用，并在适当位置对【xx】详细说明，保证行文逻辑顺畅、每个引用都有落点。

## description 编写规范

description 是技能能否被正确触发的唯一依据，按以下要求编写：

- **两要素齐全**：做什么（功能）+ 何时用（触发场景），缺一不可
- **写入触发关键词**：把用户可能说出口的词写进去（如"总结/摘要/提炼要点"），提高命中率；相邻技能职责易混时，可注明"何时不触发"
- **简明克制**：一到两句话，不写实现细节
- 反例："处理文章" ❌（无触发场景）；正例："快速总结任何文章的核心要点。当用户提供文章内容或链接、想快速获取要点时使用" ✅

## 技能标准结构

| 模块 | 必要性 | 作用 |
|------|--------|------|
| ① Frontmatter | 必须 | `name` + `description`，决定触发 |
| ② 概述 | 必须 | 1-3 句话说清技能核心目标 |
| ③ 核心原则 | 必须 | 编号列表，约束行为边界与优先级 |
| ④ 工作流程 | 按需 | 多步骤/有分支时才加，简单技能不硬加 |
| ⑤ 输出 | 按需 | 有产出物时定义格式/命名/位置/内容结构 |
| ⑥ 绝对不能做的事 | 按需 | 只写真正的硬性禁区 |
| ⑦ 自检 | 按需 | 针对该技能易错点定制的检查清单 |

各模块的具体格式模板与编写要点见 [skill-template.md](./examples/skill-template.md)。若标准结构不够用，可按需增加额外模块（如"核心概念"、"环境准备"），但必须服务于"AI 无歧义执行"。

## 工作流程

### 第一步：需求分析

1. **识别场景**：判断是**创建新技能**还是**优化已有技能**：
   - 优化：通读已有 SKILL.md 及其子文件，按【质量红线】逐条诊断，列出问题清单。
   - 创建：检查需求是否覆盖——用途、触发场景、输入、期望输出、特殊约束。
2. **澄清疑惑**：关键信息缺失或优化方向不明时，用 `AskUserQuestion` 提供选项澄清，收集到足够信息后才进入下一步。

### 第二步：设计

1. **定目标**：一句话写出该技能的唯一核心目标，后续所有内容围绕它取舍。
2. **定关键要素**：
   - `name`：全小写连字符（如 `quick-overview`）
   - `description`：按【description 编写规范】编写
   - 自由度：按核心原则第 5 条选择指令约束程度
   - 模块选择：对照【技能标准结构】只选必要模块
3. **内容分层**：规划主文件与子文件分工——大段示例/模板/参考放 `examples/`，主文件以相对路径引用。

### 第三步：写入

1. 创建新技能：在 `.claude/skills/<技能英文名>/` 目录下创建 `SKILL.md`；优化已有技能：就地重写已存在的 `SKILL.md`。
2. 若有示例/模板，在 `examples/` 目录下创建或移动，并在主文件中引用。
3. 统一【xx】内部引用标记，确保每个引用在后文都有说明。

### 第四步：质量自检

对照下面的【质量红线】逐条检查，任何一条不达标立即修正：

1. ✅ 功能目标单一明确，一句话能说清
2. ✅ description 含功能 + 触发场景 + 触发关键词
3. ✅ 每条指令具体可执行，无模糊表述（如"适当处理"、"酌情"）
4. ✅ 轻重分明：主文件精简，大段内容已分离到子文件；硬约束与建议用词区分
5. ✅ 结构合规：必须模块齐全、格式规范（编号、加粗关键字、引用标记），按需模块无冗余堆砌
6. ✅（优化场景）原技能核心功能与有用逻辑零丢失

## 输出

- **格式**：Markdown 文件
- **主文件**：`.claude/skills/<技能英文名>/SKILL.md`（创建新技能或就地重构优化已有技能）
- **子文件**：`.claude/skills/<技能英文名>/examples/` 目录下
- **内容结构**：遵循【技能标准结构】

完整生成示例参考 [example-skill.md](./examples/example-skill.md)

## 绝对不能做的事

1. 不要在用户需求或优化目标不明确时强行操作，必须先通过 `AskUserQuestion` 澄清。
2. 不要将大段示例/模板内容直接内嵌于 SKILL.md 主文件中，必须分离到 `examples/` 目录。
3. 不要省略 frontmatter 中的 `name` 和 `description` 字段，description 不得缺失触发场景。
4. 在优化已有技能时，**绝对不能删除或削弱原技能已有的有用业务逻辑**；只能做结构性重构、规范化格式和提升信息密度。
5. 不要使用模糊、有歧义的表述编写核心原则和工作流程。
6. 不要为简单技能堆砌不必要的模块（工作流程、自检等），模块数量服从实际需要。
