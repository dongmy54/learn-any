对刚结束的技能调用过程做复盘：找出做得好的、出错的、不顺畅的地方，形成【反思报告】告知用户；经用户确认后，把改进精准落地到目标技能文件中，并记录进化日志。核心目标：让技能随使用越变越好用，而不是一成不变。

## 核心原则

1. **基于事实复盘**：反思必须以本次对话中真实发生的调用过程为依据——用户的原始请求、技能实际执行的步骤、用户中途的纠正/追问/不满、最终产出与预期的差距。绝不凭空臆测"可能的问题"。
2. **先报告后动手**：必须先输出【反思报告】并列出具体改动方案，经用户确认后才修改技能文件。用户只确认部分改动时，只落地被确认的部分。
3. **最小精准修改**：每个问题只改它对应的位置（见【问题分类与落地方式】），保留技能原有核心功能与业务逻辑，严禁借进化之名重写整个技能。
4. **进化包含删减**：发现过时、重复、相互矛盾的旧条目时，合并或删除它们。技能变聪明的标志是信息密度提高，而不是内容变多。
5. **可追溯**：每次落地改动后追加进化日志，让用户随时能看到技能"是怎么一步步变聪明的"，也便于回滚错误的进化。

## 问题分类与落地方式

复盘发现的问题必须归入以下类别之一，并按对应方式落地：

| 问题类型 | 判定特征 | 落地方式 |
|----------|----------|----------|
| 触发问题 | 技能该触发没触发、不该触发误触发 | 修改 frontmatter 的 `description`（补触发关键词或"何时不触发"） |
| 流程问题 | 步骤缺失/顺序不当/冗余，导致返工或用户中途纠正方向 | 修改「工作流程」章节：增删步骤、调整顺序、补分支判断 |
| 易错点 | 执行细节出错、理解偏差、被用户纠正的具体错误 | 写入「经验教训」章节（格式见【经验教训章节规范】） |
| 输出问题 | 产物格式/位置/命名/结构不符合用户预期 | 修改「输出」章节的对应定义 |
| 知识缺口 | 缺少模板、示例或参考导致执行质量差 | 在目标技能 `examples/` 下补充子文件并在主文件引用 |

一次复盘可发现多类问题，逐一归类、逐一落地。无法归类的发现（如用户的正面反馈）只写入报告，不改文件。

## 经验教训章节规范

易错点统一沉淀到目标技能 SKILL.md 末尾的 `## 经验教训` 章节（不存在则创建），规则：

- **条目格式**：`- [YYYY-MM-DD] 一句话教训：<错误现象> → <正确做法>`
- **上限 10 条**：新增前先检查已有条目，语义重复的合并为一条（日期取最新）；超限时删除价值最低的旧条目
- **写普适教训**：剥离本次的具体上下文，写成下次任何调用都适用的规则；只对本次特例成立的不收录
- **升级机制**：某条教训若已通过修改流程/输出章节彻底根治，从本章节删除，避免双重维护

## 工作流程

### 第一步：定位目标技能

1. 从当前对话中确认本次被调用的技能名及其 SKILL.md 路径（`.claude/skills/<技能名>/SKILL.md`）。
2. 若本次对话调用了多个技能且用户未指明，用 `AskUserQuestion` 让用户选择要进化哪一个。
3. 通读目标技能的 SKILL.md 及其子文件，掌握其现有结构，为后续精准落地做准备。

### 第二步：回溯与诊断

按时间顺序回溯本次调用全过程，从四个角度采集事实：

1. **用户信号**：用户中途的纠正、追问、重试、不满或表扬——这是最高优先级的诊断依据。
2. **执行偏差**：技能实际执行与其 SKILL.md 声明的流程/输出的不一致之处。
3. **效率损耗**：返工、多余步骤、本可一次问清却反复澄清的环节。
4. **结果差距**：最终产出与用户真实需求之间的差距。

将采集到的每个问题按【问题分类与落地方式】归类，并为每个问题设计具体改动方案（改哪个文件、哪个章节、改成什么）。

### 第三步：输出反思报告

按 [reflection-template.md](./examples/reflection-template.md) 的结构输出【反思报告】，包含：做得好的、发现的问题（含分类与证据）、改动方案清单。然后请用户确认：全部落地 / 部分落地 / 不落地。

### 第四步：落地与记录

1. 按用户确认的范围，逐条执行改动方案，修改目标技能文件。
2. 在目标技能目录下的 `evolution-log.md`（不存在则创建）追加一条日志，格式见 [reflection-template.md](./examples/reflection-template.md) 的进化日志部分。
3. 落地后自检：改动是否最小精准、原有功能是否零丢失、经验教训是否符合规范。
4. 若发现目标技能 SKILL.md 已超过 200 行或结构性问题严重（多次进化打补丁导致逻辑混乱），在报告中建议用户用 `skill-generator` 做一次整体重构，本技能不代劳。

## 绝对不能做的事

1. 不要在未输出反思报告、未获用户确认前修改任何技能文件。
2. 不要臆造问题：报告中每个问题必须能指出本次调用中的具体证据。
3. 不要借进化之名重写技能或删除原有核心功能，改动只限于确认过的方案。
4. 不要让「经验教训」无限增长：超过 10 条必须合并或淘汰。
5. 不要对本技能（skill-evolve）之外未被调用过的技能做"预防性优化"。
